* The shape in one sentence

A named list of countries, each a named list of tables, each table a list keyed
by year — and of the fourteen slots the current object carries, *Stage B reads
five*: =Ft=, =Fn=, =Fm=, =lista_Am=, =lista_Z=.

The other nine — =CIn=, =CIm=, =CI=, =Recurso=, =lista_An=, =lista_A=, =Ghosh=,
=lista_BL=, =lista_FL= — are never touched by the reporting stage.
That is the single most consequential finding here: a producer that emits only
those five satisfies Stage B completely.

* 2. What =prepare_data()= requires per country

Reads exactly five slots, each indexed =[[cur_year]]= by the character year.

** The three final-demand tables: =Ft=, =Fn=, =Fm=

| # | Requirement | Imposed at |
|---+-------------+------------|
| 2.1 | each is a list keyed by every element of =years= | =support_functions.R:27,50,74= |
| 2.2 | each year holds a *=data.frame=*, not a matrix: =dplyr::rename()= is called on it | =:29,53,77= |
| 2.3 | columns named =HFCE=, =GFCF=, =GGFC=, =EXPO=, =INVNT= are present | =:30-34,54-58,78-82= |
| 2.4 | those five columns are numeric: =colSums()= follows | =:37,61,85= |
| 2.5 | column *order is irrelevant* — =select()= is by name | =:36,60,84= |
| 2.6 | extra columns are tolerated and dropped | =:36= |

The renaming is the vocabulary of the whole study and is worth stating
explicitly, because two of the five are counter-intuitive:

: C <- HFCE    I <- GFCF    G <- GGFC    X <- EXPO    E <- INVNT

*=E= is inventories, not exports; =X= is exports.*
Every later reference to =E= means =INVNT=.

** The two matrices: =lista_Am=, =lista_Z=

| # | Requirement | Imposed at |
|---+-------------+------------|
| 2.7 | each is a list keyed by every element of =years= | =:102-103= |
| 2.8 | each year holds a numeric matrix, square, of identical order $n$ in both slots | =:116= |
| 2.9 | =nrow(Fn[[year]]) == n=, so that =Am %*% Z %*% as.matrix(gastos)= conforms | =:105-116= |
| 2.10 | =lista_Am= is the *imported* technical-coefficient matrix and =lista_Z= the *Leontief inverse* — the product is meaningless if they are swapped, and nothing detects it | =:102-103= |

*2.11, the deepest silent assumption of the contract.* The product at =:116= is
positional. Nothing requires that the rows of =Fn[[year]]= are the same sectors,
in the same order, as the rows and columns of =Am= and =Z=. A candidate that
orders its sectors differently in the final-demand tables than in the matrices
produces finite, plausible, wrong numbers, and no check anywhere would fire.

** Year alignment

| # | Requirement | Imposed at |
|---+-------------+------------|
| 2.12 | every year key must parse as =as.Date(paste0(year, "-01-01"))= | =:19= |
| 2.13 | the year keys of *every* slot of *every* country must equal =years= *in the same order* | =:27-44= |

2.13 is positional, not by name: =lapply(years, ...) |> bind_rows()= builds the
rows in the order of =years= and =xts(x, order.by = dates)= then attaches dates
in the order of =dates=. A slot whose years are complete but permuted attaches
the wrong date to every observation.
A missing year does not error either: =bind_rows()= over a shorter list yields
fewer rows than =dates= has elements, and =xts()= errors only because the lengths
disagree — which is fortunate rather than designed.

* 6. Assumptions that would break silently rather than error

Ordered by how much damage they do before anyone notices.

| # | Assumption | Consequence if violated |
|---+------------+-------------------------|
| 6.1 | sector order agrees between =Fn= and the matrices (2.11) | wrong numbers, no error, no warning |
| 6.2 | year keys are complete, in order, and identical across slots (2.13) | dates attached to the wrong observations |
| 6.3 | the first country is representative (1.3, 1.4, 3.8) | failure surfaces far from its cause, or not at all |
| 6.4 | =lista_Am= and =lista_Z= are not interchanged (2.10) | a plausible, meaningless import content |
| 6.5 | =Ft= is non-zero for every component and year | =m = M / Ft= is =Inf=; the pipeline continues (=:139=) |
| 6.6 | the import share lies in [0,1] | negative domestic content; *this is issue #34*, live in 81 of 11700 cells for =E= |
| 6.7 | one currency and one base year throughout | growth rates conflate price and quantity; *unverifiable from the object* |
| 6.8 | values are levels, not indices or shares | weights and contributions lose meaning |
| 6.9 | =m=, =g=, =gm= and the contributions are *fractions, not percentages* | plots and tables off by 100; nothing asserts the unit |
| 6.10 | =country_groups= names countries that exist in =names(NIOTs)= | =filter(ISO %in% countries)= yields an empty frame and =group_plots()= writes empty figures |

6.7 and 6.8 cannot be checked from the object.
They are recorded here as assumptions the validator declares and does not test,
so that a future producer states them rather than inheriting them.
The current data is deflated to constant 1995 local prices; nothing in Stage B
verifies or even records that.

* The validator

=code/validate_niots_contract.R=, one function, no side effects:

: validate_niots(obj, strict = TRUE)

It reports the *first* violation and stops, because a candidate that fails a
structural check makes every later check meaningless.
=strict = FALSE= skips section 5's hazards (6.5, 6.6, 6.10) and checks only what
would raise an error.
The contract it encodes is =NIOTS_CONTRACT= at the top of the file: the five
slots, the five column names, and the eight countries =country_groups= requires.

Requirements it deliberately does *not* test: 2.10, 6.1, 6.4, 6.7, 6.8 and 6.9 —
sector order, matrix identity, currency, base year, levels and units.
None is decidable from the object.
They are the contract's irreducible trust in the producer, and naming them is the
most this deliverable can do about them.

* State of the verification

*What was verified.* The validator was exercised against a synthetic object of 8
countries, 3 years and 7 sectors that satisfies the contract, and against 16
mutations of it — one per requirement class. All 17 behaved as specified: the
conforming object passes; each mutation is caught with the correct message; and
the =[0,1]= violation passes under =strict = FALSE= and fails under
=strict = TRUE=.

*What is outstanding.* The demonstration ticket #26 requires — the validator
passing against the current =NIOTs= object — has *not* been run. It needs
=etc/Modelo/NIOTs_resultados.rdata=, which is on the other machine.

A synthetic object is not a substitute. It was built from this document, so it
tests that the validator implements the document, not that the document
describes the real object. Two outcomes on the real data are worth anticipating:
=strict = TRUE= is *expected to fail* on 6.6, since #34 records 81 cells outside
=[0,1]=, so the demonstration should be run at =strict = FALSE= first and the
strict failure recorded as the expected reproduction of #34.

Command to run there:

: setwd("code"); load("../etc/Modelo/NIOTs_resultados.rdata")
: source("validate_niots_contract.R"); validate_niots(NIOTs, strict = FALSE)
